## Problem and correction

The original reader deliberately raised SQLSTATE `40001` for a missing or incompatible workspace. This code means serialization failure. PostgREST/Hasql transaction handling may rerun the transaction even after the caller's ten-second deadline; a deliberately permanent condition never becomes successful. The earlier psql bridge manually manufactured an HTTP500 response and therefore could not establish the real HTTP behaviour.

The additive `busy_connected_builder_source_state_v1(uuid)` RPC returns a successful, versioned six-field projection: `version`, native `actorId`, `businessId`, `snapshotExists`, `profileExists`, and `empty`. Both original authorities are observed in one SELECT/MVCC snapshot after the original membership-row lock and current owner check. Every profile counts, including disabled profiles. Only `snapshotExists=false`, `profileExists=false`, `empty=true` can authorise the next separately reviewed source step. The RPC creates no record and returns no profile, website, business story, customer data or credential.

The function grants EXECUTE only to `authenticated`, denies PUBLIC/anon/service_role, uses the original security-definer owner authority with a fixed search path, and has a function-local two-second lock timeout. A narrowly caught actual serialization/deadlock exception becomes fatal `PT503`; it never becomes absence. Other errors propagate. No retry loop, polling, connection cancellation or termination is in this contract.

Five original function bodies keep their signatures, owner, ACL, validations, lock order, CAS predicates, writes and receipts. Nine deliberately raised failure branches change only their error code: the reader's `Workspace unavailable` becomes `P0002`; eight stale profile/website/history guards become `PT409`. Both remain failures. SQLSTATE `40001` is no longer used as a permanent business-state/CAS classification in this B3 call family. Genuine engine failures elsewhere are not globally rewritten; platform commit-level behaviour is not under the client deadline's control and must not be claimed universally bounded by this change.

It closes API EXECUTE on the new RPC without dropping the routine, any table, source record, Auth session, operation, budget reservation or receipt. It deliberately **retains** the `P0002`/`PT409` original-function corrections; restoring the known `40001` classification would restore the defect. This is a retirement rollback, not a byte restoration to an unsafe old reader.
