## Practical improvements implemented

1. **Close the remaining Work-screen cancellation bypass.** In V3.232 a *request inbox* cancellation used the correct revision-locked V3.232 transaction, but the older `setBookingStatus` Work-screen path could still call `mark_request_linked` with `bridgeState:closed` without passing the original request revision. V3.233 now rejects **all** unguarded `closed` handoffs from the authenticated Edge route. Existing booking confirmations continue through the original V3.181 durable Work RPC and still require explicit approval and a saved Work ledger.
2. **Read-only current booking preflight.** New `owner_booking_revision` owner/admin-only Edge action fetches the SAME business/app/request, its original request link and exact Work row, with no customer contact/payload. Pure `ownerBookingRevisionV3233.mjs` rejects cross-business or mismatched records, inconsistent statuses and missing confirmed Work proof. It returns current request status, timestamp and a narrow decision about whether a cancellation can be considered; it **does not** perform a cancellation.
3. **One guarded Work cancellation.** The original Work screen now performs the read-only preflight and validates it through `bookingCancelReadbackV3233.mjs`; after the owner's Cancel tap, it invokes the EXISTING `update_request_status` with the current exact saved status/timestamp. That route calls V3.232's original locked `busy_close_linked_booking_current_v3232` for request/link/events/Work cancellation in one PostgreSQL transaction. A stale click, second owner, changed ledger or replay fails closed. The Work screen **does not** silently switch to the old direct RPC.
4. **Honest uncertain-write recovery.** If the guarded cancellation response is missing or ambiguous, Work rechecks the same owner-only revision once, without repeating the write or falsely claiming that this owner's action committed. Local booking state is not marked cancelled until the transactional response is independently validated. Postcommit owner dashboard refresh is best effort and cannot retroactively make a successful booking write look failed. Actual external calendar/phone notification remains **not verified**.
5. **Simpler original owner request interface.** New pure `ownerRequestActionsV3233.mjs` supplies the same reviewing/declining/booked/draft action-visibility rules to the existing inbox cards and request-detail screen. The original authenticated route still enforces member roles, fresh revisions and permissions; this presentation function is never a permission grant. No new settings, parallel inbox, UI workflow or unnecessary jargon.
6. **Staging readiness without live execution.** New offline `prepare-booking-staging-v3233.mjs` extends V3.231's existing 11 genuine Auth/JWT cases with 11 real-world booking recovery cases (cross-tenant rejection, revoked owner, Work cancellation, stale devices, lost response, backup/restore and push disabled). It hashes seven current source files; all **22 scenarios remain not_verified** and require separate approval. It touches no hosted database, accounts, providers or credentials. There is **no new SQL migration in V3.233**; the source migration inventory remains **69**.
