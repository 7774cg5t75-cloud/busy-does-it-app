**Base:** Verified V3.237 code and Snack metadata head aa4e96db5ade44b453496b6b6c2e401f01869a2e. **Source:** Original first-party website gallery and browser layout-inspection system. **Product master:** Accessible V22.17 design agent and GitHub technical master V22.18 work priorities. **Scope:** Real offline browser checks using fictional businesses, **not** hosted real customer deployment.

## V3.237 gap
The universal Website and App planner already gave useful, grounded design directions. The mobile/tablet/desktop evaluator accepted externally supplied DOM metrics but had no captured screenshot files, independently checked byte integrity or routine actual rendered original/candidate fixture.

## What V3.238 adds
- A separate GitHub Actions browser job that renders the original fictional **Hillside Gardens** website and a coordinated alternative produced by the existing design-instruction engine. It captures full-page PNGs for **390, 768 and 1440 px** on BOTH variants. These six images are actual Chromium captures of an original first-party generated layout and its private fictional candidate, not AI artwork or simulated PNG headers.
- The existing app-owned website visual inspection script runs in Chromium for each variant and width, measures real document layout, sections, headings, contrast checks, images and links, then uses V3.237's own strict all-width comparison. A candidate with warnings introduced at any width cannot be recommended for owner visual review merely because another width improved.
- SHA-256 digest checks verify all six saved PNG files and each captured browser layout report. The receipt also binds current fictional tenant, website, exact generation, page and original/candidate HTML fingerprints. The integrity verifier checks PNG headers and pixel dimensions directly. It rejects mismatches, stale or foreign tenant records, missing files and tampering.
- An intentionally broken 1900 px wide mobile candidate is actually rendered in Chromium and must produce an overflow warning. This directly tests the negative path rather than asserting "everything looks good."
- The original production foundation, previous builder regressions, PostgreSQL 16 guest/outbox and PostgreSQL 17 Work booking rollback suites remain required. Real-browser artifacts are retained only for a short window and are exclusively fictional.

## Important evidence limits
- Screenshots are REAL Chromium screenshots of an offline **fictional fixture**. Neither they nor a SHA-256 manifest prove customer websites were rendered, accessibility-certified or customer tasks completed.
- Hashes do not attest a browser's identity or prove user-facing staging provenance. The runner controls the fixture and captures; a malicious creator could forge a manifest. Never trust an unauthorised user-provided packet.
- The candidate is a coordinated design-only edit used to exercise the safety gate, not an AI-scored winner or evidence that two production-ready layouts were shown to an owner.
- No native iOS/Android screenshot capture, hosted authenticated tenant session, production publish, credit usage, website/app mutation, email or payment was performed. No new database migration.
- No automatic redesign. Preserve owner-favoured layouts, owner locks, approved media and verified customer information. Continue to require approval and exact source revision rechecks.
