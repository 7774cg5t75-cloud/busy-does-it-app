# V3.102 — Owner creative control and safe visual-AI proposal boundaries

## Product agreement
Consistency should be in **quality**, not identical-looking websites. Initial designs can share tested principles, but owners must be able to customise their websites until they express the personality and information of their own business. The original design is a starting point, not a locked template.

## Implemented
- Add bounded explicit owner commands for individual section headings, about/contact wording, existing service descriptions, validated colours, visual layout families, service card treatments, hero position and order of existing sections.
- Retain precise owner-provided wording, allowlisted style tokens and the customer's original business facts; never invent a service, testimonial, approval, image, price or contact method.
- Recompute the customer's design plan after a change so the editable HTML and hosted HTML use the same layout decisions.
- Honour owner-selected section orders and visual families rather than overwriting them with default industry rules when generating the next version.
- Provide an optional, collapsed quick-design panel so mobile customers can try distinct looks without a lengthy page of settings.
- Existing direct voice/text BUSY requests, signed private website preview, and exact approval gates remain.
- The old draft remains private when edited. A new hosted version and public publication still require the existing approvals.

## AI design reviewer — staged, not live
- Add a server-reusable, provider-neutral **screenshot critique contract** that accepts structured visual suggestions only from a future verified model review.
- Up to three safe theme-token proposals per pass, rejecting requests to edit customer copy, identity, media, testimonials or publishing.
- Reject photo-led image compositions when there is no approved customer photo. No silent public-site editing.
- Require owner approval before applying a proposed change and preserve the original private draft.
- The contract itself **does not capture screenshots, call a vision model, create an API charge or claim that a visual model has inspected a page**. Existing designReview is still an offline structure/facts reviewer, not a screenshot AI critic.

## Next integration for genuine visual AI
1. Capture the customer's actual rendered website at iPhone and desktop widths inside authenticated, private infrastructure.
2. Use an approved vision-capable model with strict per-account allowances, privacy protections and a founder-visible provider cost meter. Send only authorised screenshot data and no unnecessary business/customer records.
3. Return a bounded, schema-checked critique of spacing, typography, image prominence, truncation, mobile navigation and call-to-action visibility.
4. Apply only proven-safe styling suggestions to a private candidate version, re-render and compare, with a hard cap on iterations and model calls. Customer fact or image changes require direct owner approval.
5. Show original and improved screenshots; explain the modifications, let the owner undo or refine them, and keep Go Live a separate explicit approval.
6. Never conflate a rules-based score with actual vision feedback; if a model is unavailable, report that visual AI review did not run.

## Explicit current limitations
- The app's text editor is **not yet a free-form, pixel-by-pixel website editor**. Users can now change more headings, wording, layouts and section order, but approved-photo selection, arbitrary new sections, full page-level editing and drag-and-drop remain future work.
- The Supabase website-generation worker must be deployed and tested before claiming hosted sites reflect these source changes.
- The vision model is not connected or charged.
- No Expo EAS cloud iPhone build has been requested as part of V3.102. All repository checks passed without using Expo build credits.
