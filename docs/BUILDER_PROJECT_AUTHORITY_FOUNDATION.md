# Future creator/project authority — staged implementation boundary

This is an implementation proposal, not an active personal workspace, permission grant or migration. Existing business builders remain first-class and retain their current membership checks.

1. Define a principal-owned workspace and a project resource before adding personal creation. Use stable independent IDs, explicit owner membership and project kind; never manufacture a business ID. Separate business membership from project membership. An authenticated principal must not infer access from possession of a project ID.
2. Introduce a trusted resource resolver that maps a project to its workspace and authoritative membership. Preserve existing business paths unchanged until their equivalent checks have integration evidence. Deny ambiguous, deleted, transferred or mismatched scopes. Every read, edit, export, preview and publication must resolve resource authority server-side.
3. Design durable storage with owner/workspace/project isolation, revision CAS, audit history, deletion/privacy rules and ownership transfer. Add adversarial isolation tests before any separately approved schema installation. Preview URLs and export artefacts need independent scoped access and expiry. Personal projects must not inherit CRM, provider credentials or business customer records.
4. Reuse canonical builder documents and finite operations after authority resolution. Bind locks, edit approvals, undo and saved candidates to resource kind, project ID and exact revision. Keep publication separate. Treat any business-data import as an explicit approved copy with provenance; do not silently link tenants.
5. Reuse the dormant Explore capability foundation with authoritative session issuance, resource audience, expiry/revocation and narrowly projected reads. Ordinary editor credentials cannot substitute for an Explore session. Deny writes/provider actions independently of conversation or tool arguments. No remote endpoint is enabled by this proposal.
6. Release incrementally: authorised informational private projects first; then revision-safe editing/export; separately reviewed publication; only later independently designed shared accounts, community records or transactions. Require integrated authority and revocation tests at each stage.

Today only project-neutral planning/discussion exists. No personal data store, account system, hosted app, generated-code executor or new tenancy model is operational. Implementation requires separate schema/release approval; this phase performs none.
