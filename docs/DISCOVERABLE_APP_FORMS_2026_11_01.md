## Protected reopening and privacy

The native adapter reuses installed Expo SecureStore57.0.4 and the original serialized private-checkpoint queue. It supports signed-in iOS/Android account/App partitions, explicitly uses iOS unlocked device-only keychain access, checks required methods, and refuses unsupported platforms. Optional native resolution occurs before loading the original SDK, so an unlinked older binary cannot crash on its throwing import. A regression proves the SDK is never loaded when the native module is missing. There is no ordinary browser storage, AsyncStorage, email matching, client-ID authority or invented encryption key.

Recovery is opt-in. Before dispatch, a maximum1,800-character record must be saved and independently read back. It contains only exact form/App/version, original challenge/token/solution, request nonce, reviewed-content digest, account scope and bounded expiry. It contains no answers, contact details or claim that submission succeeded. Only one outstanding capability/account/App is allowed; a different request cannot overwrite it.

After reopen, the controller starts with an unknown result and calls only the original receipt reader. It never resubmits automatically. Original server proof, request identity, App binding, lease, immutable historical public-safe questions and reviewed-content digest are checked before confirmation. A local record without a committed receipt stays unknown. Lost protected-store acknowledgement prevents dispatch. Account/context change fails closed. Confirmed capability clearing uses its exact nonce and a deliberate owner/customer action; device expiry/clearing is not Customer/CRM erasure.

Receipt inspections are bounded to20/challenge/hour. The retained raw reader is not directly service-callable. Recovery retains original questions and answers even after form supersession or disclosure revocation; it does not reinterpret history through newer definitions. The previous linked-proof retention correction remains mandatory. Receipt-access leases remain distinct from lawful enquiry/CRM retention and erasure responsibilities.

Important limits: unsubmitted drafts are not persisted; same-view navigation preserves them only transiently. Native encrypted storage has source/adapter tests and build evidence, not actual device acceptance. Browser durable recovery and independent standalone-bundle integration remain unavailable. A no-receipt result does not permit replay. Hosted Auth/RLS/storage, trusted ingress/WAF, consent wording, sensitive-data restrictions, retention/erasure and independent security acceptance are still required.
