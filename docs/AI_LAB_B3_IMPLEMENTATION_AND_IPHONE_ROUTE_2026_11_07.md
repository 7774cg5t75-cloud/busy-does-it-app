## Why the iPhone route is practical

An iPhone cannot safely hold a privileged Supabase service credential in a public browser application. A trusted server is still needed. The proposed server is an ephemeral standard GitHub-hosted Linux job, controlled through the owner's Safari/GitHub UI. No personal computer, new HTTP endpoint, public login page, Edge deployment or hosted database change is required to run that job after separate approval.

The existing development workflow is absent from `main`; a newly added `workflow_dispatch` cannot be assumed callable without changing the default branch. The reviewed push-marker route avoids a merge/default-branch change. It checks out the exact immutable **request event SHA**, not the older manifest source commit. Before Lab credential injection, a Python-only gate verifies the owner-approved manifest, exact run/actor/event identity and reviewed workflow/code-file hashes. The request commit must change only the inert marker. The owner must inspect the exact workflow/request commit before approving the protected job.

The Environment is fixed to **`busy-ai-lab-b3-source`**. Before any activation, independently verify its required reviewer, owner-controlled access and exact development-branch restriction. No automatic bypass/wait-only approval is acceptable. If the owner is also the request initiator, enabling “prevent self-review” would require another trusted reviewer; choose the actual arrangement explicitly. The native source safeguards remain independent of the GitHub review.

Environment secrets are read when the protected job starts, after its reviewer gate. This allows a pending run ID to be included in the final private approval before the owner approves that exact job. The approval requires exact `RUN_ID`, attempt1, actor, event SHA, immutable manifest digest and an expiry no more than one hour ahead. A new run has a different ID; a re-run has attempt2 and is denied. These checks are trusted-runner inputs, **not cryptographic origin attestation**. Anyone already holding all native credentials is a material trust boundary.

Current public repository metadata and official GitHub documentation support the standard public Linux-runner/protected-Environment route. Actual current organisation/repository policy, reviewer configuration and zero incremental runner charge still require verification before authorisation. No paid/larger runner, purchase or plan change is proposed. The Environment job also creates GitHub deployment/status bookkeeping; this must be included in future approval even though no application/Edge deployment occurs.
