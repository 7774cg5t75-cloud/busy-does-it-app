## Connected customer outcome

Original CustomerRecords now offers **Find interrupted account Enquiries**, alongside saved-reply recovery. The account list distinguishes:

* **Pending**: an eligible owner-attributed registered source, not a filed customer or verified incoming-message receipt.
* **FiledWithoutReply**: one exact supported Filed customer/enquiry association with no private target currently present.
* **FiledWithReply**: one supported actor-owned private reply with current source/reference evidence.

The owner chooses **Inspect**. Current account source/wording, state and observed revision are displayed as observations. **Keep** preserves current work. When the session has no uncertain mutation, a separate deliberate continuation rechecks the exact observation and routes through original specialists:

* Pending → **Open source for filing review** → original Quick Capture Review → another fresh Pending/source/owner-correction review → existing finite first-Enquiry filing. Opening replaces only the explicitly shown capture raw text/source label. Name, contact, service, date, note and other owner corrections stay in their original fields. Pending account registration stores only source text, not the unfiled capture corrections: a genuinely new device/session without retained fields must supply missing required identity/contact/service before filing; these values are not reconstructed or falsely described as account-recovered. A local Inbox selection is cleared rather than rebound to an account-only ID. No account source is inserted into local arrays.
* Filed without reply → **Prepare private reply** → original `useEnquiryReplyPreparation` preparation and Keep/Use → original EnquiryFollowUp editor → original reviewed finite creation/save.
* Filed with reply → **Find saved reply** → existing bounded private discovery/inspect/Keep/Open → original account-only editor → existing reviewed finite text save and server-observed continuation. The new observation is not transferred as an own-save receipt.

Quick Capture Review provides **Inspect interrupted account work** as a safe route to the original customer screen. There is no new customer editor, Inbox store, account state owner, generic restore or mutation API. Unsupported local/provider/import/catalogue/media/existing-customer cases are not normalised into the first-only subset.

Objective evidence is repeatable parent/source execution and real local SQL, not measured real customer time saved. The owner can find an already committed Pending or Filed record instead of re-registering/refiling it, reuse recorded requirements and retain capture corrections. Tests assert exact reply words and independent quote/date/website/unknown data, with global local revision remaining unchanged.

## Interrupted operations: observation is not a receipt

A matching current account record never proves that the earlier session committed it. New read-only recognition tickets cannot be consumed by mutation preparers. The session's existing uncertainty fence is neither cleared nor bypassed by discovery/readback. No automatic replay, synthetic receipt, fabricated revision increment or whole-workspace success is introduced.

| Interruption | What can be observed | Safe next action |
| --- | --- | --- |
| Registration acknowledgement lost | Eligible registered Pending source | In-place inspection/Keep; retain words. A fresh session independently selects and reviews the existing source, then files without registration replay. |
| Filing acknowledgement lost | Exact Filed association without reply | In-place inspection/Keep. A fresh session reviews the current association and prepares a first private reply, without refiling or creating another customer. |
| First reply creation acknowledgement lost | Current supported saved private wording | In-place read-only inspection, no creation replay. Fresh saved-reply discovery/Open can continue independently without attributing the earlier write. |
| Operation did not happen, source missing/deleted/unsupported | Possibly no eligible record | Empty discovery is not nonexistence or never-created evidence. Keep local work; no blind retry or automatic recreation. Same uncertain session remains blocked. |
| Account revision/source/role changed | Changed/unavailable inspection | Keep current work, rediscover and deliberately review supported current evidence. |

**Remaining limitation:** same-session writes after an unresolved mutation remain blocked, even when a result can be observed. Restart here means the independently instantiated account/session used by the tests; no device/process-death durability guarantee is claimed. A fresh session cannot reconstruct the old own-operation receipt. Durable request identity/idempotency and cross-process unknown-outcome resolution remain separately reviewed work, not a new receipt ledger.

Private target absence is not authenticated deletion history. A fresh explicit Phase65 creation after current source/absence review remains distinct from stale replay; no automatic resurrection is added. The existing stale revision/removal denials remain. Missing unsupported records never authorise restoring cached objects.

## Trusted read contract and privacy correction

New abort-fused proposal: `docs/sql-proposals/phase66-snapshot/discovery.sql`, **`busy_owner_enquiry_discover_v1(uuid,text)`**. It uses the original snapshot row, trusted UID, live owner membership and the existing membership-before-row lock boundary. Admin/member/anonymous/foreign requests deny. Reads take the same exclusive row lock as existing source helpers, avoiding SHARE→UPDATE upgrade races; no row or payload is mutated by discovery.

Response: exact business/owner/revision/schema, up to25 entries of **enquiryId/customerId/customerName/state**, `hasMore` and exact stable enquiry cursor. IDs use C byte ordering, source collections are capped at5000 Inbox/1000 customers. Customer names are bounded scalar text. No raw source stamp, private wording, contact data, entire customer array, snapshot payload or unknown nested extension is returned by discovery.

Pending/no-reply discovery requires existing server-recorded owner-manual attribution (`sourceOrigin`, `registeredBy`). Legacy unattributed/provider/imported sources are not guessed. Filed-with-reply discovery delegates to the established actor-owned supported-v2 context. Duplicate, malformed, ambiguous, foreign, unsupported and changed source records are excluded; malformed collections/unsupported schemas fail the request. Empty eligible lists do not establish absence of unsupported records. List order is not identity or authority.

Client recognition entries are WeakMap-minted, exact-content scoped, and bind actor/business/revision/original page cursor. Inspection rechecks that single bounded page at the same revision/classification, then calls the original narrow Pending/first-reply/saved-reply projection. No whole-account scan is needed just to inspect one record. Continue repeats the exact observation check and then requires original fresh mutation review. Navigation, selection, genuine typing/ABA, dirty payload, account/role/workspace and source/revision changes invalidate approvals.

A direct-route privacy gap was closed in the existing Phase65 candidate: Pending review, first-Enquiry filing and initial-reply context now reject a source explicitly `registeredBy` another actor. Merely hiding it from discovery would not protect direct RPC callers. Co-owner SQL tests exercise discovery exclusion, direct projection denial and mutation denial even when the caller possesses the exact valid source hash. Hashes are freshness evidence, not authorisation. Previously unattributed source semantics are preserved rather than retroactively inventing a creator; the new interrupted list excludes them conservatively. Actual deployed API/view/service/default-privilege coverage remains unverified.
