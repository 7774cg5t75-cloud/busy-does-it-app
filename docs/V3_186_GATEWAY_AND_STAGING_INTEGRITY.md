# BUSY DOES IT — V3.186 Gateway Evidence, Owner Decisions and Isolated Staging Integrity

Branch: \`v3.186\` based on V3.185. All changes are source-code development only. Neither production nor the real hosted staging project received any schema or Edge deployment in this sweep.

## 1. Distinguish submitted push from a customer's received notification

The existing Business App push dispatcher already saves Expo gateway submission tickets in \`busy_push_deliveries\`, alongside a tenant ID and deterministic notification key \`miniapp:{requestId}:message:{messageId}\`. In V3.185 we additionally created a durable message/outbox record, but did not compare the two.

V3.186 adds \`supabase/functions/busy-mini-apps/pushGatewayReceiptEvidence.mjs\` and an authenticated business-scoped **read-only** query in \`ownerStatus\`, matching the exact notification key across the two existing stores. This tracks:

- Intents still awaiting an attempt.
- No attempted push submission recorded.
- Submitted intents without a persisted provider ticket.
- An Expo submission ticket marked \`ok\`.
- Gateway ticket marked \`error\`.
- Partial/mixed/unrecognised ticket outcomes.

**Critical evidence boundary:** An Expo \`ok\` gateway ticket proves at most acceptance for routing, NOT Apple/Google device delivery, actual notification display, a customer opening it or a customer reading the reply. There are no device-level read receipts or provider receipt fetcher introduced here. The current review does not automatically retry pushes because that can create duplicate notifications after an ambiguous result.

The query is scoped to the current authenticated owner business, filters to the current Business App, is bounded to 100 recent outbox entries and 400 delivery rows, and returns **aggregate counts only**. No push token, target user ID, message body, phone number, provider ticket identifier or raw receipt array goes to the owner panel. Query failure is explicitly unavailable, not zero successes.

## 2. Give Business Brain an actionable, evidence-limited recommendation

\`src/core/measuredCustomerActionPriorityV3186.mjs\` combines already-stored customer journey, confirmed Work ledger and push evidence without adding a synthetic intelligence/IQ score or mixing unlike sample denominators. It prioritises:

1. A closed request with an incorrectly active Work booking.
2. An accepted booking missing the corresponding durable Work entry.
3. A customer waiting for an owner reply.
4. A rejected or over-an-hour pending notification attempt.

The panel explains why the next action matters, never changes bookings or contacts a customer by itself, and marks partial data. Importantly, a missing gateway observation **cannot conceal genuine booking/customer tasks**: the recommendation still uses the independent request and Work evidence and marks notification verification unavailable.

There is no claim of verified revenue, successful customer conversions, completed jobs, autonomous learning/retraining or actual phone delivery. Each remains a separate outcome requiring trustworthy evidence.

## 3. Verify the real staging package BEFORE approving installation

\`scripts/verify-staging-install-v3186.mjs\` checks an offline staging package generated by \`scripts/prepare-staging-install-v3180.mjs\`. It verifies the intended isolated project reference, the exact ordered SQL file set, isolation baseline first, all file lengths and SHA-256 against both the current GitHub working tree and copied files, source migration ordering, metadata risk review, and that automatic installation/production targeting remain forbidden.

Run **offline only**, without cloud keys:

\`\`\`sh
node scripts/prepare-staging-install-v3180.mjs
node scripts/verify-staging-install-v3186.mjs
\`\`\`

The V3.186 regression test deliberately alters a copied SQL file, verifies the integrity checker fails, then restores the original. The checker gives **package consistency**, not a guarantee of migrations executing successfully, grant safety, automatic install permission, or real test accounts.
