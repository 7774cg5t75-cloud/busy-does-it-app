## Connected recovered-reply outcome

Original secure bootstrap identification → CustomerRecords Find saved account replies → narrow discovery → inspect → explicit Keep/Open → original EnquiryFollowUp editor → edit → **Review private account save** → current account wording versus exact proposed wording → **Keep editing / Save reviewed wording** → existing `busy_owner_reply_text_v2` → exact target receipt → narrow metadata and exact target/source readback → another deliberately reviewed edit/save.

`useEnquiryReplyPreparation` owns genuine typing, view, source/profile and one-use review. The original private persistence adapter supplies a scoped recovered-editor context to `businessSnapshotSession`; it does not bind the recovered account into local customer arrays, create another root state owner or alter global local revision. Account identity comes from the already identified recovery workspace. Server authentication/live owner membership remain authoritative, regardless of client context.

A first recovered save obtains current revision/schema from `busy_owner_account_revision_v1`, then the existing owner-private projection at that exact revision. Opened record/source hashes, enquiry wording and prior account wording must still match. Compatible unrelated revision movement can be reviewed using freshly observed metadata; changed target/source evidence is denied. Opening a saved record is never itself permission to write.

Save approval binds actor/business/customer/enquiry/source, exact target hashes, current observed revision, draft token, genuine typing epoch, selected view and whole local-payload stamp. Typing, navigation, changed profile/source/account, permissions, independent edits after review or competing writes invalidate approval or fail server CAS. The request contains only the seven finite v2 parameters; no customer upload or whole-payload PATCH. Existing original local-reply save behaviour is retained.

An exact receipt confirms **only this private target operation**. For recovered replies, metadata and target/source readback must verify the accepted wording before the UI reports confirmed continuation. The next save again uses actual server evidence; it never guesses revision+1 to authorise another request. Local global revision, customers, quote amounts/dates, newsletters, websites, Work and preferences are not applied or cleared. The original account-only record remains transient editor context, separate from local arrays, even when the local business is different with identical record IDs.

### Uncertainty and fresh sessions

A dropped response stays unknown. No automatic retry, replay, whole-payload fallback or inferred own receipt. A deliberate read-only recheck can display currently observed account wording with an explicit **not an own-save receipt** explanation; it keeps editor words and the unresolved status. Matching text cannot resolve who committed it.

Real PostgreSQL stages commit successive recovered wordings and rediscover/read them from new connections. Original parent-flow fixtures independently reopen the second wording in a fresh application session with no reconstructed receipt. These are complementary local proofs, not a genuine browser/native cross-device or process-death durability test, nor a full application↔PostgREST end-to-end acceptance. No durable cross-session operation ledger/idempotency claim is made.

Eligible records retain the existing finite v2 constraints: exact actor-owned supported private record, matching Filed enquiry/source and supported schema, no unsupported catalogue/provenance transition. Legacy/changed/deleted/ambiguous or unsupported records cannot be silently made eligible. Account-only device saving remains unavailable. This session retains a conservative single own-target continuation basis; changing to another previously saved target may require a fresh compatible session/review rather than treating an earlier receipt as universal authority.

## First-Enquiry operation: real SQL candidate, bounded integration

New proposal: `docs/sql-proposals/phase64-snapshot/first-enquiry.sql`, with a deliberate production abort fuse; rollback and detailed contract are alongside it. Not a migration in `supabase/migrations`, not deployed and not enabled by a client flag.

The candidate uses the original snapshot row and original membership-before-row lock boundary. Server UID/live **owner** role, schema1/exact revision, finite input keys/stable identities and unchanged Pending source hash are required. Admin/member/service/foreign actors do not acquire owner-private authority. Empty/absent original customers and intake history, no previous Filed source and no colliding Work identity are required. This avoids approximating original `findCustomerMatch`, forced-new or stronger active-work reconciliation.

Supported subset: owner-reviewed first **Enquiry** from a uniquely identified, already account-recorded Pending Inbox source, text-only, without screenshot/vision/AI import or known non-Enquiry stage. Required original name/service and phone-or-email, owner corrections, note/confidence and explicitly owner-recorded date/time are retained. The server constructs original customer lifecycle/sourceRecords/activity/intakeLog fields and updates only the original Inbox item's fixed Filed fields. Unknown root/Inbox extensions, unrelated website and Work data are preserved. Omitted optional strings are not mutations of unrelated records; unknown keys, stage/consent/financial payloads and arbitrary paths are denied.

Original new-customer `contactOk:true` preference default is retained for source compatibility, **not** proof of consent or authority to contact/market. Owner date/time is recorded UTC context, not authenticated external-event/booking evidence; client time presentation requires review. Exact finite receipt identifies actor/business/customer/enquiry/source/activity/intake IDs and committed revision/stage; it returns no raw payload. Stale requests fail; repeated first filing cannot create a second customer or resurrect a retained Filed source. No duplicate ledger or blind JSON merge.

### What is deliberately not complete

Secure original `saveQuickCapture` still denies account filing and preserves its fields. The new SQL subset is **not wired to a production capture button**: there is not yet a narrow owner Pending-source review projection and one-use original capture ticket that establishes the source hash from authorised current account evidence. A local stamp, screenshot or owner assertion cannot substitute. A truly empty account also lacks a reviewed finite source-registration path. Initial filing does not invent a private reply; an initial private-reply creation contract and eligible enquiry readback are still required before the full new-account capture→file→prepare→save→recover journey exists.

Existing customer matching, forced-new, imports, screenshots/AI media, quotes/bookings/completed work and other stages remain unsupported by this subset. No fake success UI or parallel customer model was added. `fileSafeInboxItem` remains an existing-customer safe-mode specialist; it is not repurposed as first-customer creation.

Objective evidence: the new original-parent test executes actual `saveQuickCapture` plus its original date helper with inert setters. SQL parity compares every owned original Enquiry field against that parent, excluding runtime-generated IDs and timestamp encodings; SQL separately checks exact stable receipt IDs, Filed identity, lifecycle/due date and unknown/unrelated preservation. This establishes a conservative domain subset, not a complete client cutover.
