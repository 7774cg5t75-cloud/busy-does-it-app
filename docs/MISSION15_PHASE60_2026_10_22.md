## Privacy exposure and proposed boundary

Original membership-based snapshot SELECT exposes the full JSON row to a legitimate member, including owner-private replies, drafts, corrections, provenance and unknown future fields. RLS restricts rows, not nested JSON fields. Phase59 reproduced that exposure; Phase60 retains the pre-fence demonstration and tests the proposed denial afterwards.

Newly authored [review SQL](sql-proposals/phase60-snapshot/README.md) proposes:

1. Revoke raw snapshot SELECT from PUBLIC/anon/authenticated/service_role, including column grants. Only `business_id` remains SELECT-able to authenticated under existing membership RLS for original invoker bootstrap compatibility. Raw payload SELECT is denied even to an owner; approved projections are required.
2. Allow a finite shared workspace projection containing only relational business ID, workspace name and live membership role. No snapshot payload, customer contacts, owner preferences, draft content or unknown extensions are returned. This is workspace metadata, not approved marketing wording.
3. Allow a current owner-role member to read one private reply only when its stored owner ID matches the authenticated actor and its exact business/customer/enquiry association resolves. Admin is not implicitly authorised; another owner is not entitled to that record. Delegated private access remains undefined and denied.
4. Return only fixed private review fields: IDs/revision/schema, saved text, customer ID/name, filed enquiry ID/message, eligibility and opaque expected-record/source SHA-256 tokens. Do not return sourceStamp, whole customer records, arbitrary payloads or unknown nested fields.
5. Make the older target-returning v1 mutation RPC internal-only: revoke its application-role EXECUTE because its returned target could contain unknown fields. The new text-only wrapper calls its existing validation/mutation internally and projects the receipt.

All new functions use postgres ownership, fixed pg_catalog/pg_temp search_path, qualified relations, server auth.uid and live membership/record checks, explicit PUBLIC/role EXECUTE revocation and restricted entry points. Private helpers remain inaccessible. Membership locks serialize with revocation; the original snapshot row is locked for exact revision/source validation. SHA-256 tokens are compare-and-swap evidence, never authentication or historical catalogue proof. No user-editable role/capability flag authorises access.

The privacy fence has an intentional abort fuse. It also aborts if catalogue-tracked views/materialized views depend on the snapshot, because a privileged view owner can bypass base-table access restrictions. This is **not** a complete discovery mechanism for dynamic SQL, all SECURITY DEFINER functions or external services; those inventories remain activation gates.

### Admin and collaboration decisions

Current policy is deliberately minimal: owner-private access requires both current owner role and matching record owner ID. Admin/member may read shared workspace metadata only. This does not establish permissions for all collaborative customers, jobs or private drafts, nor delegate one owner's private information to another administrator. Those domain policies require explicit review before broader projections are enabled. The non-deployed fuse prevents silently breaking existing legitimate readers in the meantime.

Previously downloaded device/account copies cannot be retroactively made unreadable by a database grant change. Cache visibility, retained copies, role revocation and physical-device recovery need separate acceptance; no encryption or durable erasure is claimed.

## First finite operation connected to the original editor

Original route: saved customer reply → original customer/enquiry source resolution → existing reply editor → **Review private account save** → current-account/proposed-wording preview → Keep editing or Save reviewed wording → finite text RPC → exact target receipt.

The action is actually wired through AppController's original `enquiryReplyActions`, `useEnquiryReplyPreparation`, customer UI, existing private persistence adapter and original `businessSnapshotSession`. The production rollout constant is **false**; tests explicitly enable the source path with inert IO. No hosted action is activated.

The first supported operation is editing text of an **existing eligible version2 owner-private reply without catalogue provenance**. Missing/changed/ambiguous sources, unsupported records, revoked contact, another owner, admin role or stale revision cannot be used. Creation, upsert, other reply metadata changes and catalogue transitions are not implemented by this operation.

The owner sees the actual current account words and exact proposed words before acceptance. The original specialist supplies its real typing epoch. Approval binds scope, actor/business/role, customer/enquiry, current source/profile, draft token, selected customer, view, snapshot revision, payload fingerprint and pending-save state. Keep and Save are one-use; newer typing, navigation, corrected facts, source changes, role changes or rollout revocation invalidate approval.

A private review must be minted by the original authenticated session read; fabricated or modified packets cannot become a write ticket. The client sends only business/customer/enquiry IDs, expected revision, record/source tokens and new text. Full records remain server-side. The server reuses the original finite v1 source validator and text-leaf mutation, preserving all other JSON fields. Only fixed receipt fields and `{text}` return.

The client checks actor, business, operation, customer, enquiry, old/new revision, schema, text and record hash shape. A target receipt is not a complete snapshot receipt, a device save or a customer send. Current editor words, local saved record, independent customers/quotes/newsletters, media references and dirty fields are not replaced. Matching readback is not an own-save receipt.

Lost/mismatched acknowledgements remain uncertain. No blind retry or full-payload fallback occurs. Device replacement controls visibly disable while the account operation is unresolved; current wording remains in the editor. Receipt status is bound to the exact draft token so a newly opened draft cannot inherit another draft's confirmation. The trusted mode hides the old raw-account-check action rather than falling back to raw SELECT.

**Important continuation limit:** a target receipt does not advance the global snapshot revision or prove unrelated local work saved. The next account update needs fresh workspace/revision reconciliation and a compatible read contract. That rebase path is not complete here. No process-death or cross-device durable receipt guarantee is claimed. Current in-memory words are protected, not silently advertised as a confirmed device copy.
