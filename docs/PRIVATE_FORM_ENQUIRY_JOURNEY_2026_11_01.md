## Functioning private customer-style journey

An owner opens an exact saved private App screen containing an eligible reviewed form, enters fictional values, corrects validation errors and sees any indicative calculation through the original finite evaluator. The original App surface now also receives the same approved business-content feed. The enquiry preparation panel offers general context, exact original services, approved products/events and permitted product options, alongside separate original name/email/phone/customer-question fields.

The owner can review every active answer, original contact/wording and separate calculated outputs, then deliberately prepare the example. This produces a bounded original enquiry payload plus typed `privateForm` context. It does not write a request, create a Customer, send anything or pretend to submit. The UI explicitly says public submission is disabled. No new submission endpoint, generic writer, CRM or form-submission table exists.

The form's original eight-field, fixed-choice/type, conditional-relevance and numerical limits remain intact. Hidden conditional answers are retained only as local unfinished input and excluded from preparation; unknown fields and invalid active values are refused. All active supplied values, including approved optional fields, remain typed answers rather than being squeezed into free-text message prefixes. Customer contact/wording stays in its original destination; no arbitrary form field is guessed to establish identity or contact ownership.

Review binds owner/business/App/source revision, current immutable artifact/version/hash/state and private screen placement revision/digest. Current reads occur before review and again before confirming preparation; one-use acceptance rechecks current artifact and placement eligibility. Changing form values, customer wording, source selection or context invalidates visible review/preparation. Back navigation retains permitted unfinished values/contact details within the same exact private context; changing owner/business/App/artifact isolates the cache. Missing source authority, foreign/stale/disabled artifacts and unsupported public actions fail closed. A hash match is integrity evidence, not authenticated owner authority or a digital signature.

The finite editor now explains that answer review and contact information at the end already exist in the private rehearsal. It recognises the supported indicative-portions request without adding action permissions. Typed event-date questions remain unavailable: free text is not reinterpreted as a verified date, booking or availability check. Unsupported requests must remain saved descriptive intent or be clarified; this is finite recognition, not unrestricted AI understanding.

## Typed original-authority extension

The private preparation's `privateForm` object contains only version, App revision, placement revision/hash/screen, exact artifact identity/version/hash/state and active answers. It contains no self-granted business identity, labels, executable fields, calculated claims, send permission or mutable function-name authority. Its conservative UTF-8 size bound is below the server's 6,000-byte JSONB limit. Existing original contact/message and optional listing-context contracts are reused unchanged.

The separately fused `enquiries.sql` proposal adds no table or submission RPC. Private helpers independently read the original owned App, current membership, immutable private placement and artifact, then validate/evaluate answers through the existing PostgreSQL finite form implementation. They enforce exact enabled screens/App revision, current artifact version/state, canonical integrity, supported schema and active-only answers. Labels/options and calculated values derive from the accepted immutable form, never client assertions. Original listing candidates independently verify approved product/event/variant provenance. New form requests containing an original service selector independently match its one exact ID, current owned App revision, enabled services module and original service name before review/filing; unknown, stale, mixed and duplicate references are refused. A text prefix only selects a source; it never grants authority. Legacy non-form service paths are unchanged.

The original authenticated App enquiry reviewer, first/repeated filing authorities, Customer filed readback and canonical Work source projection are extended narrowly. Both legitimate filing callers enforce the form source guard. Renamed base functions and new private helpers lose direct PUBLIC/anon/authenticated/service-role execution grants; original externally callable functions retain their established authenticated-owner permissions and protected search paths/ownership. No arbitrary actor-ID RPC is exposed.

Within the original filing transaction, server-validated form provenance is retained on the existing original Inbox item, bound to the exact request hash, App, customer/enquiry identity and message hash. It is not a second content/customer store. Independent readback verifies that retained evidence against the exact immutable form and retained private placement. Routine original-request status updates do not replace historical answers. New form versions, supersession, disable or retaining rollback mark current eligibility false while preserving the original questions and answers for scoped historical review. JSONB integrity checks are server-canonical consistency checks; backup/restore must preserve the original authoritative data/number representation rather than round-tripping protected records through untrusted client reconstruction.

Owner filing remains deliberate, creates a separately reviewed original contact and never matches identities by name/email/phone similarity. Original CAS, receipts, independent Customer readback and unknown-outcome recovery are retained. The UI cannot acknowledge filing success when the exact form context is missing. Lost acknowledgements remain fenced and reconcile via the original request/Customer state; writes never replay automatically.
