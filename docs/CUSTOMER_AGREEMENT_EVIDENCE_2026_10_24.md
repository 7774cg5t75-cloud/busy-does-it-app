## Implemented owner task

The existing canonical Work panel now hosts a focused agreement-evidence specialist behind a separate hard-disabled `CANONICAL_OWNER_REPORT_ENABLED` gate, in addition to the disabled canonical account rollout. In synthetic local integration, an owner opens one exact current engagement, obtains server-reviewed internal quote terms, writes an attributed verbal/offline account, reviews exact wording and terms, records it once, receives its target-specific receipt and independently reads it again. A fresh session can deliberately inspect the record without inheriting the prior receipt.

The only supported class is `owner_reported_offline`, always `unverified`, always `bookingEligible:false`. There is no customer-response or independently verified acceptance writer. The captured quote is explicitly an **internal Prepared quote**, not proof of an externally presented offer. Server recording time is not an invented acceptance or observation time. Owner wording can describe what the owner recalls; the system does not certify that account.

`business_work_agreement_evidence` is subordinate to the original canonical engagement through exact business/customer/engagement keys. It is not another Work store or booking ledger. Immutable event rows retain server UUID, creator, quote revision, bounded owner statement, fixed versioned terms, source hash, complete Work-record hash and server recording time. Finite review/create/list/read functions reuse original owner membership, creator, current-source and locking authorities. A client cannot supply a verified class, accepted status, timestamp or arbitrary terms JSON. Raw reads/writes remain denied; helper search paths and RPC grants stay restricted.

The fixed terms fingerprint includes amount, planned quote date, exact wording, recorded service, original enquiry, source fingerprint and full Work-record hash. Compatible unknown fields participate in identity without being disclosed. A subsequent edit retains old captured terms and marks the report as relating to a different version. It never transfers agreement to new terms.

Bounded summary pagination excludes private owner wording. Exact reads require current creator/owner/source access. Removed, malformed, changed or privacy-restricted source evidence denies access rather than using a historical reader to disclose private reports. Reads remain observations; they cannot repair a lost operation acknowledgement. Duplicate report/version writes and stale approvals deny. No quote, customer array, legacy Work, private follow-up, Work notes, global workspace revision, request, diary or booking state is changed by report creation.

## Association and policy boundaries

The original request/link and V3.180/V3.181 durable Work ledger remain decisive. Existing persisted records do not establish a canonical quote-version/agreement-evidence/request association. Matching customer IDs, service, amount or date is insufficient. This mission therefore adds no association writer, no simulated booking relationship and no lifecycle transition. The owner sees that this protocol has not established a booking association.

A future finite association requires an approved evidence policy, exact quote/evidence/request/link/action identities, original transaction ownership, diary conflict checks, independent CAS and truthful receipts. An owner report alone cannot satisfy these requirements. No source rebase, private legacy migration or automatic historical disclosure is introduced.

Decisions still required before activation: permissible use of owner attestations; evidence classes and verification authority; offer/presentation provenance; correction/retraction of immutable reports; retention/erasure; legacy private authorship and migration authority. The current first slice allows one immutable owner report per engagement/creator/quote version. Same-version corrections are unsupported: do not change a quote merely to circumvent that restriction. No existing follow-up or Work-notes wording is reinterpreted or migrated.
