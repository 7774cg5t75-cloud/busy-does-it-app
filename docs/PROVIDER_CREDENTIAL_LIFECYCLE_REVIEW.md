# Provider preparation and credential lifecycle boundaries

Phase Four connects the original signed-in staging runtime to a fixed, disabled-by-default metadata/preparation mode in the original social gateway. The finite SQL rechecks and locks current owner membership. The client cannot choose actor identity, RPC names or callback destinations. Original production prototype status now fails closed; it cannot read raw credential-bearing tables or a global prototype queue. Metadata is deliberately labelled preparation-only, even when historical records say connected. No provider exchange, publication, disconnect or token replacement is exposed by this new mode.

The new mode requires exact staging project configuration and the server value `BUSY_PROVIDER_PREPARATION_ENABLED=reviewed-metadata-only`. This value is not set or deployed by this mission. Status, reviewed intent creation and receipt inspection are the only permitted actions. Current private session transport keeps bearer credentials out of AppController; session generation and business scope are checked before and after each operation.

Standard SHA-256 PKCE preparation and strict callback-parameter review are implemented and tested, including the RFC7636 vector. They do not persist a verifier or permit an exchange. Google documentation recommends S256. Meta-specific PKCE, provider-subject evidence, code exchange and remote revocation require provider-specific independent review. Neither email nor editable metadata establishes account ownership.

**Credential readiness remains blocked.** Original social token columns remain the canonical storage authority, but this candidate does not supply application-layer encryption or a trusted key lifecycle. No invented key, client key, bespoke cipher or second credential store is introduced. Before any real connection, select and approve a platform-managed encryption/key boundary; restrict decrypt authority to finite server operations; define rotation/key-version rollback, authenticated audit events without token values, retention/erasure and verified restore. Database encryption at rest alone is not claimed to solve service-role disclosure.

Existing replacement transactions never inherit an old account's refresh token or assets. Revision/subject-bound disconnection records local state separately from provider revocation. Unknown exchange/revocation outcomes must remain reserved/inspectable and must not trigger destructive or billable retries. Historical credentials are not deleted or rotated by source changes. Auth-user deletion/retention consequences and stale refresh-token destruction require explicit reviewed authority. Metadata inspection should log operation outcome and correlation identifiers only, never tokens, raw state, authorization codes or private content.

Calendar integration remains blocked: its original authoritative storage/permission closure is not accepted. All historical provider denial fences and ten direct-model denial sites remain. No global re-enable switch exists. AI gateway/cost-controller gates are unchanged.

References: https://developers.google.com/identity/protocols/oauth2/native-app and https://developers.google.com/identity/protocols/oauth2/resources/best-practices . Documentation is guidance, not evidence of real provider acceptance.

## Phase Five implementation decision

Provider secret persistence remains deliberately unimplemented until a platform-managed key boundary is selected and independently checked. Supabase Vault is a documented candidate: authenticated encrypted secrets, provider-managed keys outside the database, and a decrypted view whose grants are themselves a critical trust boundary. Its availability, effective ACLs, operational costs, backup restoration, key rotation and support guarantees have not been verified for this project. Do not create a local encryption key, grant general service access to `vault.decrypted_secrets`, or migrate historical tokens automatically.

A future finite adapter must bind a secret reference to current business/owner/provider subject, exact connection revision, OAuth-state digest, approved callback and S256 challenge. Persist the verifier only server-side; claim state once, decrypt solely for that claimed exchange, retain ambiguous exchange state and never retry blindly. Provider-subject evidence must come from the documented authenticated provider response. Replacing an account needs fresh review and a new connection revision; do not inherit prior refresh tokens. Local disconnection, remote revocation and verified erasure must have separate states and receipts. Rotation should publish a new managed secret version only after verified replacement, retain the prior version solely under an explicit recovery window, and never log tokens, codes or verifiers. Retention/erasure and Auth-account deletion must be approved before activation; no historical data was destroyed here.

The source preparation mode still cannot exchange or persist secrets. Calendar/social exchanges remain closed. This reviewed dependency is an activation blocker, not a reason to prevent secure offline builder/intelligence development. Reference: https://supabase.com/docs/guides/database/vault . Signed Storage URLs are bearer capabilities unaffected by Auth key changes; cache/expiry limits are documented at https://supabase.com/docs/guides/storage/serving/downloads and https://supabase.com/docs/guides/storage/cdn/smart-cdn . No instant revocation claim is made.
